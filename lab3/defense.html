Код для показу

Вхід і поточний користувач. lab3/Program.cs:83 (рядки 83–87).

auth.MapPost("/login", async (LoginRequest r, AuthService s) =>
    await s.LoginAsync(r) is { } token ? Results.Ok(token)
        : Results.Problem("Невірний логін або пароль.", statusCode: StatusCodes.Status401Unauthorized));
auth.MapGet("/me", [Authorize] (ClaimsPrincipal user) =>                // дані про користувача беруться з claims токена
    new MeDto(user.FindFirstValue("sub")!, user.Identity!.Name!, user.FindFirstValue("role")!));

Після успішного входу сервер видає токен. Захищений маршрут /me читає з нього ім’я та роль.

Тут дві різні перевірки. Спочатку сервер підтверджує особу за логіном і паролем. Коли клієнт уже передає токен, сервер перевіряє його, а далі вирішує, чи дозволено цій людині читати або змінювати конкретні дані.

Перевірка прав на ресурс. lab3/Program.cs:231 (рядки 231–235).

protected override Task HandleRequirementAsync(AuthorizationHandlerContext ctx, OwnerRequirement req, int ownerId)
{
    if (ctx.User.IsInRole("Admin") || ctx.User.FindFirstValue("sub") == ownerId.ToString()) ctx.Succeed(req);
    return Task.CompletedTask;
}

Перевірку проходить власник запису або адміністратор. Тому той самий запит до чужого завдання дає звичайному користувачу 403, а адміністратору повертає дані.

У перевірці беру ідентифікатор користувача з токена й порівнюю його з ідентифікатором власника в базі. Так рішення залежить від того, хто увійшов і кому належить запис. Роль Admin має окремий дозвіл.

1. Enter → реєстрація та невдалий вхід

У першій команді під час реєстрації alice передаю role: Admin. У відповіді бачимо role: User і статус 201. Це означає, що роль нового користувача призначив сервер.

Нижче йдуть дві помилки. Некоректний запит на реєстрацію повернув status: 400 і список проблемних полів. Запит на вхід із неправильним паролем повернув status: 401, бо сервер не підтвердив облікові дані.

2. Enter → успішний вхід

У відповіді на успішний вхід є accessToken, expiresAt і роль. Це підписаний JWT із терміном дії. Наступні захищені запити передають його в заголовку Authorization.

У декодованому вмісті токена є sub — ідентифікатор користувача, а також name, role і exp. Останній запит до /api/auth/me повертає короткий JSON із користувачем alice та роллю User. З цієї відповіді бачимо, яку особу сервер розпізнав за токеном.

Показ результату

3. Enter → перевірка прав доступу

На початку цього виводу запит до /api/tasks без токена отримав 401. Далі з токеном taras бачимо його завдання, а з токеном alice — порожній список із відповіддю 200. Сервер прийняв запит, але в цього користувача ще немає власних завдань.

Нижче запит alice до /api/tasks/1 дає status: 403. Сервер знає, хто звернувся, і перевірка показала, що завдання чуже. Коли той самий маршрут викликає адміністратор, у виводі з’являються номер і назва завдання.

4. Enter → HTTPS, CORS і хеші паролів

У відповіді на запит через HTTP бачимо 307 і заголовок Location з адресою, яка починається на https://. Сервер перенаправив запит на захищене з’єднання.

Нижче Access-Control-Allow-Origin містить localhost:5173. Це адреса браузерного клієнта, якому дозволено звертатися до API. У таблиці користувачів стовпець HashPrefix виводить початок хешу пароля. Імена секретів виводяться окремо, а їхні значення замасковані.
