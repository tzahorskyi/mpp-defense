Код для показу

Читання завдань. lab2/Program.cs:42 (рядки 42–45).

var tasks = app.MapGroup("/api/tasks").WithTags("Tasks");
tasks.MapGet("/", ([AsParameters] TaskQuery q, TaskService s) => s.ListTasksAsync(q));
tasks.MapGet("/{id:int}", async Task<Results<Ok<TaskDto>, NotFound>> (int id, TaskService s) =>
    await s.GetTaskAsync(id) is { } t ? TypedResults.Ok(t) : TypedResults.NotFound());

Маршрут /api/tasks передає параметри фільтра в сервіс. Запит за номером повертає завдання або 404.

Ідентифікатор у шляху потрібен, коли я звертаюся до конкретного запису. Фільтри передаю в рядку запиту, бо вони визначають, яку частину списку повернути. Обидва маршрути звертаються до одного сервісу.

Створення завдання. lab2/Program.cs:46 (рядки 46–49).

tasks.MapPost("/", async Task<Results<Created<TaskDto>, ValidationProblem>> (TaskRequest r, TaskService s) =>
    await s.CreateTaskAsync(r) is { } t
        ? TypedResults.Created($"/api/tasks/{t.Id}", t)
        : TypedResults.ValidationProblem(NoProject));

Після збереження API повертає 201 і адресу нового завдання. Якщо проєкт не існує, повертає помилку валідації.

У запиті на створення клієнт передає назву, пріоритет і проєкт. Відповідь містить ідентифікатор, який згенерувала база. Існування проєкту перевіряю перед збереженням, щоб кожне завдання було прив’язане до реального проєкту.

1. Enter → читання. Покажи JSON зі списком проєктів і завдань.

Через GET отримую JSON зі списком проєктів і завдань. Для кожного проєкту сервер одразу повертає загальну кількість завдань і кількість виконаних. Клієнту не потрібно рахувати це самому.

У виводі для завдання видно назву, пріоритет, стан і назву проєкту. Цих полів досить, щоб клієнт показав готовий список, навіть якщо користувач ще не відкривав окремого проєкту.

2. Enter → фільтр і пошук. Покажи сортування за пріоритетом і результат пошуку лр.

Фільтр залишив невиконані завдання з пріоритетом від двох. Найвищий пріоритет іде першим, бо в запиті задано sort=-priority. Пошук «лр» знаходить і назви з великими «ЛР».

У першому запиті умови діють разом. Виконані завдання пропускаються, навіть якщо в них високий пріоритет. У другому запиті пошук іде за назвою або описом. Для кирилиці порівнюю текст без урахування регістру.

Показ результату

3. Enter → створення, зміна й видалення. Покажи відповідь 201, оновлене завдання і 404 після видалення.

Створив завдання «Пробіжка 5 км». Сервер повернув 201 і адресу нового запису в заголовку Location. Після PUT повторний GET показав пріоритет 3 і статус «виконано». Видалення дало 204, а наступний GET — 404, бо запису вже немає.

Зверну увагу на 204 після зміни й видалення. Це успішна відповідь без тіла, тому новий стан перевіряю окремим GET. У першому випадку бачимо змінений запис, у другому отримуємо 404.

4. Enter → перевірка помилок. Покажи поле errors у відповіді. Якщо цього достатньо, на наступній паузі заверши показ через Ctrl+C.

Для некоректних даних сервер повертає 400. У полі errors видно, що саме треба виправити, наприклад завеликий пріоритет або закоротку назву.

У першому прикладі «x» має менше трьох символів, а пріоритет 7 виходить за межі від 1 до 3. Окремо перевіряю посилання на неіснуючий проєкт. В обох випадках сервер відхиляє запит до того, як створити запис.
