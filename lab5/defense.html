Підготовка перед захистом

1. На Mac. Через Spotlight відкрий Docker Desktop. У Terminal введи ці команди. docker info має вивести розділ Server, а список Buildx — активний збирач. У VS Code відкрий lab5/Dockerfile, lab5/.dockerignore та lab5/compose.yaml.

cd ~/Desktop/unik/MPP
docker info
docker buildx ls

2. Збірка образу заздалегідь. Введи цей блок перед захистом. Він піднімає локальний реєстр, якщо потрібно, збирає образ для arm64 і amd64 та виводить його платформи. Дочекайся обох рядків Platform. Цей етап може тривати кілька хвилин.

cd ~/Desktop/unik/MPP/lab5
if ! docker container inspect mpp-registry >/dev/null 2>&1; then
  docker run -d --name mpp-registry -p 5001:5000 registry:2
else
  docker start mpp-registry
fi
docker buildx build --platform linux/arm64,linux/amd64 -t localhost:5001/mpp-tasks-api:1.0 --push .
docker buildx imagetools inspect localhost:5001/mpp-tasks-api:1.0

3. Початок показу. У терміналі Mac введи команди нижче. Залиш вікно Docker Desktop відкритим, щоб за потреби перемкнутися на список контейнерів. Скрипт чекає Enter перед кожним кроком.

cd ~/Desktop/unik/MPP

Доброго дня. Я Тарас Загорський, група ІПЗ-31. У п’ятій лабораторній упакував API у Docker. Dockerfile збирає образ, а compose.yaml запускає API і PostgreSQL разом.

Код для показу

Збірка і запуск образу. lab5/Dockerfile:9 (рядки 9–14).

RUN dotnet publish -a $TARGETARCH -c Release -o /app --no-restore && mkdir /data

# ---------- Етап 2: лише runtime ASP.NET Core, без SDK і вихідного коду ----------
FROM mcr.microsoft.com/dotnet/aspnet:10.0
WORKDIR /app
COPY --from=build /app .

Компілюю застосунок під архітектуру, задану в TARGETARCH. У фінальний образ копіюю готову збірку та запускаю її в ASP.NET Runtime.

Вихідний код і засоби збірки потрібні на етапі SDK. У фінальному контейнері достатньо скомпільованого застосунку та середовища виконання. Тому той самий Dockerfile використовую і для збирання, і для підготовки робочого образу.

Старт API після бази. lab5/compose.yaml:15 (рядки 15–22).

api:
  build: .
  image: mpp-tasks-api:1.0
  depends_on:
    db:
      condition: service_healthy          # API стартує, коли PostgreSQL готовий
  ports:
    - "8080:8080"

Compose чекає, поки PostgreSQL пройде перевірку стану. Потім запускає API та відкриває порт 8080.

У налаштуваннях підключення до бази використовую ім’я сервісу db. Так контейнери знаходять один одного в мережі Compose. А порт 8080 потрібен для запитів до API з комп’ютера.

1. Як зібрано образ. Натисни Enter. У виводі знайди два FROM, dotnet publish і рядок COPY --from=build. Нижче покажи .env у списку виключень.

Термінал виводить Dockerfile. У першому FROM бачимо образ .NET SDK, а далі — dotnet publish, який збирає програму. Другий FROM використовує ASP.NET Runtime, і команда COPY --from=build переносить туди готову збірку.

Під Dockerfile виводиться .dockerignore. Тут є .env, файли бази, bin та obj. Docker виключає їх із контексту збірки, тому в образ не потрапляють локальні налаштування і зайві файли.

2. Підняття API й PostgreSQL. Натисни Enter і дочекайся таблиці docker compose ps. Шукай сервіс db зі станом healthy і сервіс api з портом 8080. За потреби розгорни проєкт у Docker Desktop → Containers.

Після запуску в таблиці docker compose ps бачимо два сервіси, db і api. У рядку db є позначка healthy. Compose дочекався, поки PostgreSQL готовий приймати з’єднання, і запустив API.

Під таблицею виводяться налаштування контейнера API. У рядку підключення Host=db видно, що програма звертається до бази за іменем сервісу в мережі Compose. Пароль у цьому виводі замаскований.

Показ результату

3. Перевірка й запис у базі. Натисни Enter. Знайди Healthy у відповіді, потім id нового «ЛР5 Docker» в JSON. Зістав його з Id у таблиці PostgreSQL.

Під запитом до /health бачимо Healthy. Це означає, що API відповідає і перевірка з’єднання з PostgreSQL пройшла.

Після POST у JSON бачимо номер і назву «ЛР5 Docker». Нижче у таблиці з PostgreSQL є рядок із тією самою назвою й номером у стовпці Id. Це підтверджує, що завдання з відповіді API справді записано в базу.

4. Перезапуск і збереження даних. Натисни Enter. Після повторного запуску знайди в результаті пошуку той самий id, який був на кроці 3.

У терміналі видно, що docker compose down видалив контейнери, а up створив їх знову. Після запуску API повертає результати пошуку за словом «docker».

У цьому списку знову є «ЛР5 Docker» з тим самим ідентифікатором, що був до перезапуску. Контейнер PostgreSQL новий, а каталог із даними Compose підключив із попереднього тому. Тому завдання залишилося на місці.

5. Дві архітектури. Натисни Enter. У списку маніфестів знайди linux/amd64 і linux/arm64. Нижче покажи окремі результати запуску aarch64 та x86_64.

У виводі перевірки образу під одним тегом є дві платформи, linux/arm64 і linux/amd64. Нижче перший uname -m показує архітектуру комп’ютера.

Після команди запуску з --platform linux/arm64 бачимо aarch64. Після запуску з --platform linux/amd64 — x86_64. Це вже результати з контейнерів. Тег той самий, а Docker запускає відповідний варіант образу.

Підсумок видно в трьох місцях. API відповів Healthy, запис зберігся після перезапуску, а під одним тегом бачимо два варіанти образу. Це підтверджує роботу контейнерів, персистентність даних і підтримку двох архітектур.

Наприкінці. Скрипт сам зупиняє контейнери цього Compose-проєкту. Том PostgreSQL залишається для наступного запуску.
