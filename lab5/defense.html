Доброго дня. Я Тарас Загорський, група ІПЗ-31. У п’ятій лабораторній упакував API у Docker. Dockerfile збирає образ, а compose.yaml запускає API і PostgreSQL разом.

Код для показу

Збірка і запуск образу. lab5/Dockerfile:9 (рядки 9–14).

RUN dotnet publish -a $TARGETARCH -c Release -o /app --no-restore && mkdir /data

# ---------- Етап 2: лише runtime ASP.NET Core, без SDK і вихідного коду ----------
FROM mcr.microsoft.com/dotnet/aspnet:10.0
WORKDIR /app
COPY --from=build /app .

Компілюю застосунок під архітектуру, задану в TARGETARCH. У фінальний образ копіюю готову збірку та запускаю її в ASP.NET Runtime.

Вихідний код і засоби збірки потрібні на етапі SDK. У фінальному контейнері достатньо скомпільованого застосунку та середовища виконання. Тому той самий Dockerfile використовую і для збирання, і для підготовки робочого образу.

Старт API після бази. lab5/compose.yaml:15 (рядки 15–22).

api:
  build: .
  image: mpp-tasks-api:1.0
  depends_on:
    db:
      condition: service_healthy          # API стартує, коли PostgreSQL готовий
  ports:
    - "8080:8080"

Compose чекає, поки PostgreSQL пройде перевірку стану. Потім запускає API та відкриває порт 8080.

У налаштуваннях підключення до бази використовую ім’я сервісу db. Так контейнери знаходять один одного в мережі Compose. А порт 8080 потрібен для запитів до API з комп’ютера.

1. Enter → Dockerfile. Покажи два етапи збірки в терміналі.

На першому етапі SDK збирає .NET-застосунок. У другий етап копіюю тільки готову збірку. Тому фінальний образ менший, а .NET SDK потрібен лише під час збірки.

Файл .dockerignore виключає .env, локальні файли бази й вихідні папки збірки з контексту Docker. Через це вони не потрапляють у збірку навіть на етапі, де Dockerfile копіює файли проєкту.

2. Enter → Docker Compose. Дочекайся статусів контейнерів.

У списку видно два контейнери. Спочатку PostgreSQL має пройти перевірку стану. Лише після цього Compose запускає API, яке підключається до бази.

У терміналі дивлюся на стан healthy для PostgreSQL. Пароль і конфігурацію підключення API отримує через змінні оточення при запуску. Тому образ серверної програми можна використати з іншими значеннями конфігурації.

Показ результату

3. Enter → перевірка API. Покажи відповідь /health і завдання «ЛР5 Docker» у виводі PostgreSQL.

На /health отримав Healthy. Перевірка охоплює і з’єднання з базою. Через API створив завдання «ЛР5 Docker», а у виводі PostgreSQL видно відповідний рядок.

Це дві різні перевірки. Healthy показує, що API зміг підключитися до бази. Збіг назви й ідентифікатора у відповіді API та в таблиці PostgreSQL підтверджує, що запит справді записав завдання.

4. Enter → перезапуск. Дочекайся повторного пошуку завдання.

Compose зупинив і видалив контейнери. Після повторного запуску пошук знову знаходить те саме завдання, бо дані PostgreSQL лежать у Docker volume, який Compose підключив до нового контейнера.

Порівнюю ідентифікатор завдання до й після перезапуску. Залишився той самий запис. У PostgreSQL каталог даних прив’язаний до іменованого тому, тому видалення контейнера не видаляє самі дані.

5. Enter → дві архітектури. Покажи linux/arm64, linux/amd64 та результати uname.

Під одним тегом є образи для двох платформ. Запуск із параметром --platform linux/arm64 показує aarch64, а --platform linux/amd64 дає x86_64. Це видно у виводі uname всередині контейнера.

У виводі реєстру видно два варіанти під одним тегом. На Apple Silicon arm64 працює нативно, а amd64 запускається через емуляцію. Користувач може вказати ту саму назву образу, а Docker підбере варіант під платформу.
